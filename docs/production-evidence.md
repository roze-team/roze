# Production Evidence

Roze must not claim full production stability without reproducible evidence.
This page defines the evidence required before a module moves from `beta` to
`stable`.

## Current Evidence Status

Current repository evidence is limited to unit tests, compile smoke tests,
generator smoke tests, release-gate checks, and local production smoke scripts.
This is enough for internal pilots, but not enough for a public claim such as
"battle-tested in production".

Do not publish fabricated 24h/72h results. If a result is not generated by a
repeatable command or backed by a real deployment report, mark it as missing.

## Required Long-Run Reports

Before a production-stable claim, each stable runtime area must have at least
one long-run report:

| Area | Minimum run | Required workload | Required failure injection |
| --- | --- | --- | --- |
| Gateway | 24h before beta-to-stable, 72h before broad public stable | proxy traffic, retries, fallback, rate limit, breaker, load shedding, hot reload | upstream 5xx, timeout, slow response, config reload, upstream recovery |
| MQ | 24h before beta-to-stable, 72h before broad public stable | publish/subscribe, ack, nack, retry, DLQ, replay, idempotency | consumer failure, broker restart, duplicate publish, delayed delivery |
| Config Center | 24h before beta-to-stable, 72h before broad public stable | watch, polling fallback, valid reload, invalid reload, section events | Etcd disconnect, invalid payload, slow listener, failed listener |
| Lifecycle | 24h before beta-to-stable | start, drain, shutdown, failed task, timeout hooks | stuck task, signal shutdown, hook timeout |
| Generated services | 24h before beta-to-stable | generated REST/RPC/search/model/stream projects under load | regenerate/update, config reload, dependency loss |

## Report Template

Every report must include:

- Roze Git revision.
- Rust toolchain and OS.
- Command used to start the run.
- Dependency versions and topology.
- Workload shape: RPS, payload size, topic count, consumer count, route count.
- Duration.
- Success criteria.
- Error budget.
- p50/p95/p99 latency where applicable.
- Throughput where applicable.
- CPU, memory, file descriptor, and connection trends.
- Restart count.
- Leak check result.
- Failure injection timeline.
- Final verdict: pass, fail, or inconclusive.

## Pass Criteria

Long-run evidence can be marked `pass` only when:

- No unbounded memory growth is observed after warm-up.
- No goroutine/thread/task leak equivalent is observed for the runtime.
- Error rate stays within the documented error budget.
- Recovery after injected failure completes within the documented recovery
  objective.
- Metrics and logs are sufficient to explain every injected failure.
- No manual intervention is required unless the scenario explicitly tests
  operator rollback.

## Repository Placement

Store reports under:

```text
docs/evidence/<yyyy-mm-dd>-<area>-<duration>.md
```

Large raw artifacts such as flamegraphs, logs, and metric exports should be
linked from the report instead of committed directly.

## Release Gate Relationship

`scripts/release-gate.sh` proves that high-signal automated checks pass. It is
not a replacement for long-run production evidence.

A release can be cut without long-run reports only when the release notes say
the affected modules are `beta`, `scaffold`, or `planned`.
